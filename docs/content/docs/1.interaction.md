### Purposefully Unopinionated

Legato aims to leave UI up to the developer. 

This means you can write your own UI with Webview technologies, frameworks like ICED, Bevvy, or EGUI, or even easily make terminal applications with [Ratatui](https://ratatui.rs/).

There will likely be a UI editor in the future but this is not immediately planned and works a bit against the intention of the project.

### Controlling your Applications

**In summary, you have ~6 ways to change values in the runtime:**

#### Message Passing

These are drained once per audio block.

Simply send a message to your node like so:

```rust
let (app, mut frontend) = LegatoBuilder::<Unconfigured>::new(config)
    .build_dsl(&graph)?;

frontend.send_node_msg(
    "example",
    NodeMessage::SetParam(ParamPayload {
        param_name: "freq",
        value: RtValue::F32(440.0),
    }),
)?;
```

`send_node_msg` returns `FrontendError::NodeNotFound` for an unknown alias, and `FrontendError::QueueFull` if the audio thread hasn't drained the message queue (512 slots) yet. A message for a param the node doesn't know is ignored.

You'll notice that we are sending `RtValue` to the audio thread. These are designed so that they will not allocate or drop from the runtime, potentially causing clicks or pops.

#### Param Store

Additionally, you can use the param node to get a smoothed f32 value. 

This is good for say something like a gain value, referenced by mutliple nodes.

Internally this uses atomics, and mirrors what various VST frameworks use.

```rust
frontend.set_param("freq", 440.0)?; // outputs 440.0 audio rate at the next block

// Or look the key up once, e.g. for a UI slider
let key = frontend.get_param_key("freq")?;
frontend.set_param_by_key(key, 220.0)?;
let current = frontend.get_param_by_key(key)?;
```

#### External Input

You can add an audio rate external input with a SPSC, like so:

```rust

let (producer, consumer) = rtrb::RingBuffer::new(4096 * 4); // 4 frames of headroom

let (app, _) = LegatoBuilder::<Unconfigured>::new(config)
    // Adding the audio input here
    .register_audio_input("one", consumer, 1, config.block_size)
    .build_dsl(&graph)?;

AudioInterface::builder(&host, config)
    // Starts the input thread. Skip this if managing your own input.
    .input(InputSpec {
        producer,
        chans: 1,
        device: DeviceSelection::Default,
    })
    .build(app)
    .expect("Failed to start audio")
    .run_forever(); // Blocks here
```

#### Loading External Buffers

We can also load in external buffers from another thread. These are then reference counted and therefore safe to use in the runtime*.

Samples are decoded with [ffmpeg](https://ffmpeg.org/download.html), so an `ffmpeg` binary must be on your `PATH`. `load_sample` returns `AudioSampleError::FfmpegNotFound` if it isn't, `PathNotFound` for a missing file, and `FailedDecoding` with ffmpeg's error otherwise.

```rust
let (app, mut frontend) = LegatoBuilder::new(config)
    .set_midi_runtime(midi_rt_fe)
    .build_dsl(&graph)
    .expect("graph should build");

frontend
    .load_sample(
        "main",
        Path::new("../samples/string.wav"),
        2,
        config.sample_rate as u32,
    )
    .expect("Could not load sample!");
```

#### MIDI Applications

Full MIDI specification is still quite a bit aways, but for the time being you can control your applications with a MIDI runtime like so:

```rust
let midi_rt_fe = start_midi_thread(
    256,
    "my_port",
    MidiPortKind::Index(0), // or MidiPortKind::Named("Keystep")
    MidiPortKind::Index(0),
    "my_port",
)?;

let (app, mut frontend) = LegatoBuilder::new(config)
    .set_midi_runtime(midi_rt_fe)
    .build_dsl(&graph)
    .expect("graph should build");
```

With no MIDI hardware attached, `MidiPortKind::Index(0)` returns `MidiError::InvalidPort`. On macOS and Linux, `MidiPortKind::Virtual` creates a port named `port_name` that a DAW or another app can connect to instead.

And later in your graph, you can use the MIDI nodes like so:

```legato
// ...
midi {
    poly_voice { chan: 0, voices: 3 }
}

// We use port striding here to target multiple voices
poly_voice[0:10:3] >> voice(*).gate
poly_voice[1:10:3] >> voice(*).freq
```

#### Custom Nodes

If you need additional logic, and the above to not suffice, consider a custom node.
